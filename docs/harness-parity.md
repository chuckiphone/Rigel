## Statuses

| Status | Meaning |
|---|---|
| `pass` | The adapter path exists and a focused test or fixture covers it. |
| `fail` | The vendor supports the capability, but Rigel does not wire it up yet. |
| `not-supported` | Rigel's adapter or client has no path to the capability. |

## What each column checks

- **Approvals** — Rigel answers the harness's own permission request: the native approval bus, Codex app-server approvals, Claude's MCP permission tool, or ACP `session/request_permission`.
- **Streaming** — deltas arrive while the turn runs: native provider streams, Claude `stream-json`, Codex app-server deltas, or ACP `session/update` message chunks.
- **Usage** — a `usage` transcript item is written from harness-reported data. ACP reports context used/size, not a billed input/output split; that limit is recorded as-is.
- **Resume** — a new invocation continues the harness's own conversation. Native resumes Rigel's session and paused turn; Codex and Claude record a thread/session id but never pass it back; the ACP client starts every turn with `session/new`.
- **Tools** — tool calls and results become transcript items. Native executes Rigel's tool set; external harnesses run their own tools and Rigel records them.

## How this is checked

`cargo test -p rigel-cli --test harness_parity` compares this file with `rigel_adapters::parity::markdown()` and pins each expected status. `cargo test -p rigel-adapters parity` checks every cell against `registry::capabilities`; a capability that silently flips therefore fails the check.

Codex approvals are app-server only; its `exec --json` fallback has no approval channel. Claude approvals require the MCP permission tool the CLI writes per run. ACP approvals are answered only with an option the agent offered, otherwise `cancelled`.
